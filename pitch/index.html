Мы делаем расширение для «1С:Бухгалтерии для Казахстана». Оно закрывает одну конкретную ручную операцию — подбор номенклатуры во входящих счетах-фактурах. Посмотрите на эту строку: поставщик прислал гель для посуды, а бухгалтерия у себя учитывает его как жидкое мыло. Ни одна модель этого не угадает по тексту. Наша система подставляет правильно, потому что учится на истории самой базы.

Проблема

ЭСФ загружен.
Колонка «Товар» — пустая.

В разделе G поставщик пишет свои названия. Пока колонка не заполнена, поступление по ЭСФ не создать — бухгалтер подбирает каждую строку вручную.

Строки — из генератора тестовых ЭСФ проекта

Получить ЭСФ в 1С уже не проблема — для этого есть штатный сервис. Проблема дальше. В разделе G поставщик пишет свои названия, а колонка «Товар» пустая. Пока её не заполнили, документ поступления не создать. Бухгалтер подбирает строку за строкой вручную. По оценке Первого БИТа, обработка десяти ЭСФ в день занимает около часа. Сколько из этого часа — именно подбор номенклатуры, мы измерим на пилоте.

Почему это не решается поиском по тексту

Правильный ответ знает
только ваша бухгалтерия

История уже есть в базе: проведённые ЭСФ прошлых лет с заполненной колонкой. Один прогон — и память работает с первого дня.

Мы разметили строки по сложности. Часть легко сопоставить по тексту. Но есть три класса, где текст бессилен. Корзина: сок, йогурт и сыр уходят в одну позицию «Продукты питания». Своя логика: гель для посуды — это мыло, просто потому что так решили в этой бухгалтерии. И позиции, которой нет вовсе, — тут правильный ответ «не знаю». Ключевая идея: историю не нужно копить. Проведённые ЭСФ с заполненной колонкой уже лежат в базе клиента. Один прогон — и система работает с первого дня.

Как работает

Первый уверенный ответ
останавливает конвейер

  1. 01Памятьчто эта бухгалтерия уже выбирала для этого поставщика
  2. 02Точное совпадениепосле нормализации единиц, фасовки и сокращений
  3. 03Нечёткоетокены, триграммы, бренды; размер и цвет — жёсткий фильтр
  4. 04Модель ИИтолько на остаток — следующий этап, интерфейс слоя уже заложен
зелёная — подобрано уверенно жёлтая — варианты, выбор в один клик красная — не найдено

Лучше уточнить, чем ошибиться. Малый отрыв между кандидатами — строка уходит человеку, а каждое подтверждение пополняет память.

Всё внутри 1С. Память — регистр сведений в той же базе. Без внешних серверов: данные бухгалтерии никуда не уходят.

Строка проходит слои по порядку. Сначала память — что эта бухгалтерия уже выбирала для этого поставщика. Потом точное совпадение. Потом нечёткое: нормализуем единицы и фасовку, а размер и цвет считаем жёстким фильтром — поло XL никогда не станет поло M. Первый уверенный ответ останавливает конвейер. Если между кандидатами малый отрыв, строка становится жёлтой и уходит человеку. Языковую модель подключим на остаток — интерфейс для неё уже заложен. Всё работает внутри 1С: данные бухгалтерии никуда не уходят.

Доля строк, подобранных автоматически и верно. Расчёт: node src/run-bench.js — 92 строки синтетических ЭСФ с эталоном, порог 0,75, память из 138 строк. Не данные клиента.

Мы проверяем не «сколько угадали», а «сколько ошиблись молча». Это главное число, и оно ноль во всех сценариях. Без памяти правила подбирают 48 процентов строк. С памятью из прошлого периода — 77. Строки «своей логики»: было 0 из 6, стало 5 из 6. Честно: это синтетика из нашего генератора с эталоном, 92 строки. На реальных документах цифры будут другими — их и покажет пилот.

Аналоги есть, и мы их изучили. Штатный сервис 1С забирает ЭСФ. У Первого БИТа есть доработка, которая создаёт поступления; номенклатуру там сопоставляют вручную, а затем запоминают по поставщику. BuhGPT отвечает на вопросы бухгалтера — это другая задача. Наш фокус — строки, которые раньше не встречались, и запуск сразу на истории базы. Превосходство не заявляем: сравним на одних и тех же документах.

Считаем время вместе с проверкой

Экономия = время сейчас − (проверка жёлтых + исправления)

  • доля строк, принятых без исправлений
