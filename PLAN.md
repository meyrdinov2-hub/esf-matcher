# Расширение 1С: подбор номенклатуры в полученных ЭСФ

Рабочий план. Форм-фактор изменён с отдельного веб-инструмента на
расширение конфигурации «Бухгалтерия для Казахстана, ред. 3.0».

## Задача

В полученном ЭСФ, раздел G, поставщик присылает свои наименования товаров.
Рядом пустая колонка «Товар» — туда нужно подставить позицию из нашего
справочника номенклатуры. Совпадений по тексту почти нет, сопоставление
делается вручную, построчно, десятки строк на документ.

Пока эта колонка пустая, штатная обработка «Создания поступлений /
Счет фактур» отработать не может. Отсюда ощущение «автоматизировано, но
всё равно руками».

## Решение в одну фразу

Расширение подставляет номенклатуру прямо в форме документа ЭСФ,
подсвечивая уверенные и сомнительные строки, и учится на том, что
бухгалтерия уже сопоставила за прошлые годы.

## Главное отличие от аналогов

У IRBIS-SOFT (ближайший конкурент) в планах развития записано «расширенная
функция сомнения — точнее работа с неоднозначной номенклатурой». То есть
задача у них признана нерешённой. Их ИИ рассуждает из общих знаний о мире.

Но сопоставление вида

    ГЕЛЬ FREYA ДЛЯ МЫТЬЯ ПОСУДЫ  →  Средство для мытья рук Чистозря

не выводится ни из какой модели мира. Оно выводится только из того, что
в этой конкретной бухгалтерии так уже делали.

**Ключевая идея: историю не нужно накапливать — она уже есть в базе.**
Сотни проведённых ЭСФ с заполненной колонкой «Товар» лежат у клиента с
прошлых лет. Разовый прогон по базе — и память заполнена в первый же день,
без периода обучения и без единого внешнего запроса.

Замеры на синтетике (`src/run-bench.js`), класс `idiosyncratic`:
правила — 0 из 6, правила + история — 5 из 6.

## Архитектурное решение: всё внутри 1С

Рассматривались два варианта.

**A. Автономное расширение.** Правила и память целиком во встроенном языке,
память — регистр сведений в той же базе. Никаких внешних сервисов.

**B. Гибрид.** Правила и память в 1С, языковая модель снаружи по HTTPS.

**Выбран A, с заделом под B.**

Обоснование: на стенде правила + память дают 77% автоподбора при нуле
тихих ошибок. Модель нужна только на остаток, и её вклад тем меньше, чем
полнее память. При этом вариант A не требует серверов, не имеет
ежемесячной стоимости, работает за любым файрволом и полностью снимает
вопрос «куда уходят данные бухгалтерии» — а это главный барьер доверия.

Вариант B остаётся возможным позже: интерфейс слоя `llm` в конвейере уже
предусмотрен, подключается без перестройки остального.

## Состав расширения

### 1. Регистр сведений «СоответствияНоменклатурыПоставщиков»

Накопленная память сопоставлений — сердце решения.

| Поле | Тип | Роль |
|---|---|---|
| Контрагент | измерение | у разных поставщиков одно наименование значит разное |
| НаименованиеНормализованное | измерение | результат нормализации строки поставщика |
| НаименованиеИсходное | реквизит | как прислал поставщик, для отчётов |
| Номенклатура | ресурс | что выбрал человек |
| КоличествоПодтверждений | ресурс | чем чаще, тем надёжнее |
| ДатаПоследнего | реквизит | для разбора спорных случаев |

### 2. Обработка «Первичное обучение»

Разовый прогон по проведённым ЭСФ: собирает пары «наименование поставщика ↔
выбранная номенклатура» и заполняет регистр. Запускается один раз при
внедрении, потом по желанию.

Именно эта обработка даёт эффект «работает с первого дня».

### 3. Общий модуль «СопоставлениеНоменклатуры»

Порт движка, уже написанного и проверенного на JS:

- нормализация наименований — единицы, фасовка, проценты, сокращения,
  склейки на границе алфавитов (`src/normalize.js`);
- разбор атрибутов — размер и цвет как **жёсткий фильтр**, не как признак
  похожести (`src/match/attrs.js`);
- мера близости — вхождение токенов, триграммы, латинские бренды,
  совпадение фасовки (`src/match/pipeline.js`);
- пороги уверенности и отрыва от второго кандидата.

Порядок слоёв: память → точное совпадение → нечёткое → (позже) модель.
Первый уверенный ответ останавливает конвейер.

### 4. Расширение формы документа ЭСФ

- кнопка «Подобрать номенклатуру» над табличной частью раздела G;
- раскраска строк: зелёная — подобрано уверенно, жёлтая — есть варианты,
  красная — не найдено;
- по жёлтой строке — список кандидатов с оценками, выбор в один клик;
- каждое подтверждение человека пишется в регистр.

Принцип: **лучше уточнить, чем ошибиться.** Строка с малым отрывом между
кандидатами не заполняется автоматически — она уходит на проверку.
Тихая ошибка дороже отказа: жёлтую строку бухгалтер посмотрит, зелёную —
нет.

### 5. Отчёт об обработке

Сколько строк подобрано автоматически, сколько отправлено на проверку,
сколько позиций не найдено. Те же три числа, что считает стенд.

## Песочница для тренировки

Пока казахстанской конфигурации нет, механика отрабатывается на российской
«Бухгалтерии предприятия учебной» 3.0.35.27 — она уже развёрнута.

Инструменты (`tools/`):

- `onec.ps1` — пакетные операции: создать базу, развернуть `.dt`, выгрузить
  конфигурацию в XML, загрузить и выгрузить `.cfe`. Сама находит платформу.
- `scan_config.py` — разбор выгрузки: ищет документы, у которых в табличной
  части есть ссылка на номенклатуру. Работает по типам реквизитов, а не по
  именам, поэтому переживёт смену конфигурации.

Проверено на деле: выгрузка `DumpConfigToFiles` в учебной версии
**работает** — 27 307 файлов, 1.2 ГБ. Значит, на казахстанской базе точные
имена объектов получим командой, а не вечером в конфигураторе.

Мелочь, которую стоит помнить: демо-база с данными пакетные операции не
отдаёт («Пользователь ИБ не идентифицирован», имя не угадывается), а чистая
идёт сразу. Для разработки держим чистую базу.

**Аналог целевого объекта в российской конфигурации:**

| | Россия (песочница) | Казахстан (цель) |
|---|---|---|
| Документ | `ПоступлениеТоваровУслуг` | полученный ЭСФ |
| Табличная часть | `Товары` (21 реквизит) | раздел G |
| Реквизит | `Номенклатура` типа `CatalogRef.Номенклатура` | колонка «Товар» |

Готового регистра соответствий номенклатуры поставщиков в конфигурации нет —
проверено, велосипед изобретать придётся.

## Этапы

| Этап | Содержание | Зависит от |
|---|---|---|
| 0 | Развернуть учебную платформу + конфигурацию, найти точные имена объектов ЭСФ | покупка учебной версии |
| 1 | Регистр сведений + обработка первичного обучения | этап 0 |
| 2 | Порт движка в общий модуль | готово на JS |
| 3 | Расширение формы документа | этапы 1–2 |
| 4 | Отчёт об обработке | этап 3 |
| 5 | Слой модели на остаток — опционально | замеры после этапа 4 |

## Что остаётся на JS

Код в `src/` не выбрасывается. Он остаётся:

- **эталонной реализацией** — логика отлаживается там, где итерация
  занимает секунды, а не перезапуск конфигуратора;
- **стендом** — генератор синтетики с эталоном и замер трёх исходов;
- **перекрёстной проверкой** — фикстуры из генератора выгружаются в файл,
  прогоняются через порт в 1С, результаты сверяются с JS. Расхождение
  означает ошибку порта.

## Что нужно приобрести

**«1С:Бухгалтерия 8 для Казахстана. Учебная версия. Редакция 3.0» —
4 500 тг**, коробка «книга + диск». В комплекте учебная платформа 8.3 и
сама конфигурация. Продаётся у партнёров: [1c-rating.kz](https://1c-rating.kz/price/),
[1c-sapa.kz](http://1c-sapa.kz/pricelist), [1cbit.kz](https://www.1cbit.kz/1csoft/1s-bukhgalteriya-8-dlya-kazakhstana-uchebnaya-versiya/).

Редакция 3.0 — та же, что у клиента. Цифровой загрузки нет, только
коробка. Скачиваемых демо-баз казахстанской бухгалтерии в открытом
доступе не нашлось: у франчайзи есть онлайн-демо в веб-клиенте, но это
для просмотра, не для разработки.

Это единственный дешёвый легальный источник конфигурации. Всё остальное
идёт через партнёрский договор.

## Известные ограничения учебной версии

- **потолок 2000 записей на таблицу** — бьёт по нам сильнее всего:
  справочник номенклатуры и регистр соответствий как раз крупные объекты.
  Тестировать придётся на подмножестве, поведение на реальных объёмах
  учебная версия не покажет;
- **конфигурация учебной версии не обновляется** — её релиз 3.0.x будет
  старее боевого (в 2026 идут 3.0.69 … 3.0.73). Если расширение
  заимствует объект, появившийся в свежем релизе, в учебной базе его
  просто не окажется. Проверять совместимость придётся на стороне
  клиента;
- один сеанс, нет клиент-серверного режима, нет COM-соединения, нет
  хранилища конфигурации;
- замедленная работа;
- нельзя вести реальный учёт — для песочницы неважно.

По HTTP: в официальных списках ограничений исходящие запросы и
`HTTPСоединение` **не упомянуты**, жалоб на форумах нет — то есть
исходящие, скорее всего, работают. А вот *публикация* HTTP-сервисов
(входящие запросы) почти наверняка недоступна: она требует публикации
информационной базы на веб-сервере, чего в учебной поставке нет.
Для варианта B это означает: схема «1С сама опрашивает сервер» —
реализуема, схема «сервер стучится в 1С» — нет. К счастью, первая и так
лучше.

## Запасной вариант платформы

У 1С есть бесплатная **комьюнити-лицензия** для разработчиков
(developer.1c.ru, платформа 8.3.23.1596+): полная функциональность без
лимита в 2000 записей, ограничение — 3 сеанса. Доступность регистрации
из Казахстана не проверена.

Даже если она доступна, проблему конфигурации это не решает — её всё
равно неоткуда взять, кроме учебной коробки. Отдельно нужно выяснить,
допустимо ли лицензионно разворачивать учебную конфигурацию на
платформе с комьюнити-лицензией: это сняло бы потолок 2000 записей,
но может противоречить условиям учебной поставки.

## Открытые вопросы

- точное имя объекта документа полученного ЭСФ и структура его табличной
  части в редакции 3.0 — выяснится сразу после установки;
- выгружается ли `.cfe` из учебной версии. Прямого подтверждения нет;
  косвенно в пользу — 1С пишет, что форматы информационных баз учебной и
  коммерческой версий не отличаются, и допускает разработку прикладных
  решений на учебной платформе;
- размер реального справочника номенклатуры у клиента — упрёмся ли в
  лимит учебной версии при тестировании;
- сколько строк ЭСФ в месяц проходит через бухгалтерию — нужно, чтобы
  понимать, окупается ли всё это вообще. Пока это главная неизвестная
  во всём проекте.
